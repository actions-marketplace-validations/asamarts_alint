# v0.10 bench coverage — three scenarios for the publish gate

Status: **Implemented** — lands with the atomic Phase 5 commit
(this commit). Draft predecessor at `36638d51`. Three new
scenarios (S11/S12/S13) + scenario-keyed overlay hooks +
parse-and-build round-trip tests for every Scenario + xml-path
micro-bench supplement, all as designed.

D5 of the audit-decision set says **bench coverage GATES the
v0.10 release**. `xtask bench gate` (the programmatic
publish-quality gate) only inspects rows from the macro corpus
(`xtask bench-scale` → `results.json`). Today that corpus runs
`scenarios/s1..s10.yml` — none of which exercise any of the eight
v0.10 rule kinds. Zero coverage for `registry_paths_resolve` /
`cross_file_value_equals` / `ordered_block` /
`generated_file_fresh` / `import_gate` / `command_idempotent` /
`xml_path_*` / `pair_hash` in either macro scenarios or the micro
`alint-bench` corpus.

This phase closes that gap.

## Shape (decided)

Three new scenarios, grouped by **dispatch class** — the same
axis the engine routes on, so a regression in one class is
isolated to one cell and a regression across all of them is
visibly correlated. Per-rule-kind isolation (8 scenarios) was
rejected as ~double the corpus wall time for diminishing
isolation value; one-mixed-scenario was rejected as losing all
regression isolation.

### S11 — v0.10 cross-file (3 kinds)

The cross-file dispatch class. Three kinds, each on the regular
synthetic monorepo (workspace `Cargo.toml` + N member packages,
already generated by `alint_bench::tree::generate_monorepo`):

- **`registry_paths_resolve`** — workspace `Cargo.toml` is the
  registry; `[workspace].members = ["packages/p*"]` is the entry
  list. Each member directory exists, so the rule walks the
  full index N times for the existence check and stays silent.
  Perf signal: the registry parse + per-entry existence check at
  scale (`crate::extract` literal/non-literal split, `crate::io`
  `read_capped` gate on the manifest, full-index path lookup).
- **`cross_file_value_equals`** — workspace root
  `Cargo.toml`'s `[workspace.package].edition` must match each
  member `Cargo.toml`'s `[package].edition`. Members already
  inherit `edition = "2024"` from the synthetic generator, so
  the rule is silent — the perf cost is in the N+1 file reads
  + N TOML parses + N value comparisons.
- **`pair_hash`** — workspace root carries a single
  `manifest.sha256` (one valid sha256 hex line + a path that
  does not match any actual source); `source: "packages/p*/Cargo.toml"`,
  `target: manifest.sha256`, `mode: contains`. Most sources
  miss the single in-target hex → many violations. Real perf
  signal: hashing every member `Cargo.toml` + scanning the
  target. The bench measures the rule machinery; the violation
  count is a side effect.

S11 reuses the existing regular tree. The `manifest.sha256`
fixture is written by an S11-only overlay step in `run.rs`
right after tree generation. No new tree generator, no perturbation
of S1..S10 cell counts.

### S12 — v0.10 per-file (3 kinds)

The per-file dispatch class — file-major fan-out, the path the
`v0.9.3` work was designed to make flat. Three kinds over the
same `**/*.rs` scope already used by S6:

- **`ordered_block`** — a `// alint:keep-sorted start` /
  `// alint:keep-sorted end` block guard on `**/*.rs`. The
  synthetic `lib.rs` / `mod_NNNN.rs` files contain no markers,
  so the rule scans each file once and stays silent. Perf
  signal: per-file marker scan in the per-file dispatch loop.
- **`import_gate`** — Rust preset (`extract: rust`,
  `allow: ["std::*", "alint_*::*"]`). The synthetic files
  contain no `use` lines, so all extractions are empty and the
  rule is silent. Perf signal: the regex extraction pass per
  file.
- **`xml_path_equals`** + **`xml_path_matches`** — both on a
  single root-level `.csproj` written by an S12-only overlay
  step. One scoped check (`$.Project['@Sdk']` matches
  `Microsoft\.NET\.Sdk` / equals `Microsoft.NET.Sdk`). The
  overlay is one file, so xml-path cost is fixed-O(1) per run
  — the perf signal is the cross-version stability of the XML
  family's parse + path-evaluate path, not its scaling shape.

S12 reuses the regular tree + one overlay file. xml_path
coverage at scale would require a per-package .csproj fan-out
(perturbing the 100k tree's file count and breaking cross-version
baselines); the trade-off is not worth it — xml's scaling
properties are covered by the micro-bench in 5C.

### S13 — v0.10 single-shot (2 kinds)

The single-shot dispatch class — `generated_file_fresh` and
`command_idempotent` run **once per check regardless of N**;
they shell out to a user-declared program. Benching the
shelled-out program is not a useful signal; benching alint's
spawn machinery is. Both rules use `command: ["true"]` (the
POSIX no-op): zero work in the child, so the row measures
`fork+exec+wait+stdout-parse` for one invocation.

S13 runs on the regular tree at the standard sizes. The
single-shot rules add a fixed cost per run; the tree-walk
dominates the row. The perf signal is **cross-version
stability** of the spawn path (regressions in
`crate::spawn::run_capturing`, the `crate::io::read_capped`
walk gate, or the engine's dispatch glue would show up as a
sustained delta).

## Wiring

```
xtask/src/bench/scenarios/s11_v010_cross_file.yml          (new)
xtask/src/bench/scenarios/s12_v010_per_file.yml            (new)
xtask/src/bench/scenarios/s13_v010_single_shot.yml         (new)
xtask/src/bench/mod.rs:
  + const SCENARIO_S11 / S12 / S13 = include_str!(...)
  + Scenario::{S11, S12, S13} variants
  + parse / label / description / config_yaml extensions
  + mod tests: every Scenario::*.config_yaml() round-trips
    through alint-dsl as a valid v1 config.
xtask/src/bench/run.rs:
  + scenario.setup_overlay(&tree_root) hook (no-op default;
    S11 writes manifest.sha256; S12 writes one root .csproj).
```

No new dependencies. No change to existing scenarios. No
change to tree generators. The `requires_polyglot_tree` /
`requires_git_repo` model is preserved — neither new scenario
flips either flag.

## Phase split

- **5A** — this design doc (Status: Draft).
- **5B** — atomic landing: 3 new YAMLs + mod.rs/run.rs wiring +
  CHANGELOG `[Unreleased]` Added entry. Status flips here.
- **5C** — micro-bench supplement (optional within Phase 5): add
  xml to `crates/alint-bench/benches/structured_query.rs`; add
  the three v0.10 cross-file kinds to
  `crates/alint-bench/benches/cross_file_rules.rs`. Provides
  developer-time regression detection independent of the macro
  gate.
- **5D** — preflight validation: the scenario-parse unit tests
  in 5B catch include_str!/YAML mistakes at `cargo test` time
  (preflight green is sufficient evidence). No bench-scale run
  is wired into preflight; the publish-grade run is a Phase 7
  release-cut prerequisite.

## Phase 7 prerequisite (recorded for the v0.10 cut)

Before tagging v0.10:

1. On a fingerprint-clean runner, execute
   `xtask bench-scale --sizes 1k,10k,100k --scenarios S1,S2,...,S13`
   (all scenarios, both modes — the bare invocation default).
2. Commit `results.json` + per-size markdown under
   `docs/benchmarks/macro/results/<os-arch>/v0.10.0/`.
3. Run `xtask bench gate <results.json>
   --baseline docs/benchmarks/macro/results/<os-arch>/v0.9.23/results.json`.
4. The gate must report `gating_failures = 0` (within-run CV ≤
   10 % for 100k cells, `min_ms` regression ≤ +15 % vs v0.9.23
   for ≥10k cells present in both reports — new S11/S12/S13
   cells have no baseline and are correctly skipped by the
   per-cell key match in `gate::evaluate`).

## Open questions resolved on this design

- **Q: Per-rule isolation (8 scenarios)?** No — bench corpus
  ~doubles, isolation value diminishes once the dispatch class
  is identified.
- **Q: xml_path at 100k scale via per-package .csproj?** No —
  perturbs file counts across S1..S10, breaks cross-version
  baselines. Single root-level fixture for the macro gate;
  scaling shape covered by micro-bench.
- **Q: Single-shot kinds at real work (`go vet` or similar)?**
  No — benches the shelled-out program, not alint. `true` is
  the right baseline for spawn-machinery regression detection.
- **Q: Publish-grade run as part of Phase 5?** No — wall time
  is hours and the result is a release artefact. Phase 5 lands
  the scenarios; Phase 7 runs them.
